# 地图表现层 Demo 需求

## 这次真正要验证什么

这次需求的核心不是“大地图动态事件”“势力行为”“时间流逝”这些上层系统。

那些系统后面当然重要，但它们不是当前最让人没底的地方。

当前最需要先验证的是：

> 这个项目能不能做出一个让人相信可以继续填内容的地图表现层。

也就是说，先不要急着讨论世界会不会动态变化，而是先证明：

- 地图不是只能由简单像素块拼出来。
- 场景能承载正常的建筑、地形、植被、水域、人物和氛围效果。
- NPC 和主角能以正常角色素材播放行走和动作动画。
- 建筑、树木、山石等对象能遮挡角色。
- 地形能阻挡行走，也能区分水域、台阶、高低层、桥梁等情况。
- 地图资源可以被持续替换和扩展，而不是每加一个场景都重新写死逻辑。

如果这个底座不先做出来，剧情和设定就很难继续稳定落地。因为看着现在这种临时像素块地图，很难判断后续地标、城镇、山门、关隘、江湖场景到底能不能真正做出来。

## Godot 侧大致支持情况

以下不是要求完全照这些节点实现，只是说明这些能力在 Godot 里通常不是从零发明。

Godot 本身可以支持：

- 导入任意图片资源。
- 使用 `Sprite2D` 显示单张图片。
- 使用 `AnimatedSprite2D` 或 `AnimationPlayer` 播放角色帧动画。
- 使用 `TileMapLayer` 或多个节点组合地形和装饰层。
- 使用 `StaticBody2D`、`CollisionShape2D`、`CollisionPolygon2D` 做碰撞阻挡。
- 使用 `Area2D` 做交互区、触发区、传送区。
- 使用 `NavigationRegion2D` 或导航多边形做寻路。
- 使用 `CanvasItem` 的 `z_index`、`y_sort_enabled` 做前后遮挡排序。
- 使用 `GPUParticles2D`、`CPUParticles2D` 做云、雾、落叶、雪等粒子效果。
- 使用 `Camera2D` 做镜头跟随、边界、缩放。

所以这批需求不一定是“技术上很难”，关键是要把项目自己的地图制作规范和 demo 跑通。

## 当前工程路线：运行时生成与外部编辑器

目前工程的地图场景不是在 Godot 编辑器里手工摆出来的，这不是单纯遗漏，而是更接近“数据驱动 + 运行时生成”的路线。

现在的结构更接近：

```text
Boot.tscn
-> 运行时加载数据
-> 切到主菜单
-> 切到具体地图场景
-> 地图脚本读取 data/maps.json
-> 运行时创建背景、障碍物、玩家、NPC、出口、拾取物
```

因此打开 Godot 编辑器时，只看到一个很薄的 `Boot` 场景，或者打开 `mountain_pass.tscn`、`foot_village.tscn` 时也只看到一个挂脚本的空 `Node2D`，这是当前实现方式导致的。

这能解释为什么“开始游戏后能看到地图”，但“编辑器里看不到地图”：

- 游戏运行后，脚本会动态创建地图内容。
- 编辑器静态视图里，只显示 `.tscn` 文件里已经保存的节点。
- 当前大部分地图对象没有保存在 `.tscn`，而是从脚本和 `data/maps.json` 生成。

这个方式适合快速验证功能，也更适合 AI 直接修改纯文本配置。

因此下一阶段不一定要改成“在 Godot 编辑器里配置地图”。更合理的方向可能是：

> 做一个项目自己的地图/内容编辑器，用来编辑同一套结构化配置，再由游戏运行时转换成 Godot 场景内容。

这个外部编辑器的优势是：

- 配置文件可以保持纯文本或结构化数据，AI 更容易生成和修改。
- 不需要剧情负责人直接理解 Godot 场景节点、`.tscn`、资源导入细节。
- 可以针对本项目定制字段，比如地标、书线、势力、NPC、传送点、遮挡、碰撞、事件条件。
- 可以做“一键预览/转换/校验”，比直接手写 JSON 或直接摆 Godot 节点更稳。
- 后续可以把地图配置、剧情配置、对象状态配置放在同一套工作流里。

所以问题不是“必须能在 Godot 编辑器里看到地图”，而是：

> 必须有一个可视化工具，让地图负责人能看见、摆放、校准地图内容，并且这个工具产出的配置能被 AI 和游戏运行时共同使用。

Godot 编辑器仍然可以作为运行调试和底层开发工具，但不一定是主要内容编辑工具。

剧情对象可以继续数据驱动：

- NPC
- 对话入口
- 拾取物
- 传送点
- 任务条件
- 剧情状态

地图表现层也可以继续数据驱动，但需要外部编辑器解决可视化编辑、预览和校验问题。否则只靠手写 JSON，后续很难做正式视觉调校。

## 当前已有能力与仍需补齐

从当前本地代码看，部分能力已经有雏形：

- 主角已经使用 `CharacterBody2D`。
- 主角已支持从 `assets/characters` 加载角色帧图片。
- 找不到角色图片时，会回退到程序生成的临时帧动画。
- 地图对象已从 `data/maps.json` 读取并运行时生成。
- NPC、战斗触发点、出口、告示、商店、拾取物等交互对象已经数据化。
- 地图边界和部分障碍物已经用 `StaticBody2D` + `CollisionShape2D` 实现。
- 战棋地形已有 `terrains.json`，包含草地、水、桥、树、山等地形属性。

但这些不等于地图表现层已经完成。仍需要重点确认或补齐：

- 探索地图的地形层是否已经真正数据化，而不只是少量脚本写死的矩形障碍。
- 建筑、树木、牌楼等对象的遮挡和前后层级是否已实现。
- 水域、桥、高低层、台阶等在探索地图里是否有可视化和行走规则。
- 外部地图编辑器是否已经能可视化摆放底图、对象、碰撞、遮挡、交互区。
- 编辑器产出的配置是否能直接被游戏读取，或稳定转换成游戏配置。
- 是否有调试显示来查看碰撞区、交互区、传送区、对象 id。
- 是否有数据校验脚本检查资源路径、对象 id、对话 id、任务 id、传送目标。

也就是说，已实现的部分应该在需求里标注为“已有雏形/需确认体验”，而不是重复要求从零做。

## 第一批：资源导入和场景底图

先明确地图到底支持哪几种制作方式。

至少需要验证两种路线中的一种，最好两种都能跑：

### 方案 A：大图底图模式

适合大地图、世界地图、手绘城镇、特殊场景。

需求：

- 支持导入一张较大的地图底图作为场景背景。
- 支持在底图上放置 NPC、建筑前景、碰撞区、交互点、传送点。
- 支持相机在大图内移动，不能露出地图外的空白区域。
- 支持给大图配置行走区域和阻挡区域。
- 支持后续替换底图图片，不影响交互点和对象逻辑。

示例场景：

```text
山脚村镇_大图版
背景：一张完整村镇底图
可行走区域：村路、广场、客栈门口
阻挡区域：房屋、墙、树、河流
交互点：客栈、药铺、告示牌、NPC
传送点：村口、山道入口、官道入口
```

### 方案 B：图块拼接模式

适合野外、地牢、山路、重复性地形。

需求：

- 支持用图块拼地图，但不能只停留在纯色块测试。
- 支持地表层、装饰层、遮挡层、碰撞层分开。
- 支持图块有不同地形属性，比如草地、石路、水、山壁、桥。
- 支持不同图块对应不同行走规则。
- 支持后续替换 tileset 美术资源。

示例场景：

```text
山道_图块版
地表层：草地、山路、石阶
阻挡层：山壁、树、岩石
装饰层：草丛、路牌、破旗
遮挡层：大树树冠、屋檐、山门牌楼
水域层：溪流、浅水、深水
```

## 第二批：角色动画和动作表现

当前不能只支持像素点 NPC。

需要验证角色可以使用正常图片素材，并播放不同方向和动作帧。

最低需求：

- 主角支持上下左右四方向行走动画。
- 主角支持站立待机动画。
- NPC 支持静止站立，最好也支持简单行走。
- 每个角色可以配置自己的图片或帧动画资源。
- 支持角色尺寸不完全相同。
- 支持角色与场景对象的前后遮挡关系。

建议预留动作类型：

- idle
- walk
- run
- talk
- attack
- hurt
- interact
- sit
- special

第一版不用全部实现，但资源和脚本结构最好不要只写死 `idle` 和 `walk`。

角色资源配置可以长这样：

```text
character_id: hero
display_name: 主角
sprite_set: res://assets/characters/hero/
directions: up, down, left, right
animations: idle, walk
collision_size: 16x12
interaction_radius: 24
```

## 第三批：建筑、遮挡和前后层级

这是地图能不能看起来像正常 RPG 场景的关键。

需要验证：

- 角色走到建筑、树木、牌楼后方时，会被前景遮挡。
- 角色走到对象前方时，会显示在对象前面。
- 大树、屋檐、山门、桥洞等对象可以拆成底部碰撞和顶部遮挡。
- 遮挡不是简单全图盖住，而是能按角色位置正确排序。

建议 demo 里至少做这些对象：

- 一栋房屋，有屋身碰撞和屋檐遮挡。
- 一棵大树，有树干碰撞和树冠遮挡。
- 一个山门或牌楼，角色能从下面走过并被部分遮挡。
- 一座桥，角色能在桥上走，水在桥下。

这批验证通过后，后面城镇、门派、山寨才有制作信心。

## 第四批：碰撞、路径阻断和可行走区域

地图必须明确哪里能走、哪里不能走。

需要支持：

- 建筑阻挡。
- 山壁阻挡。
- 树木阻挡。
- 水域阻挡或特殊通行。
- 桥梁可通行。
- 台阶、坡道、门洞等特殊通行点。
- 地图边界阻挡。
- NPC 阻挡或半阻挡。

至少要有一个调试显示模式：

- 显示碰撞区。
- 显示可行走区域。
- 显示交互区域。
- 显示传送区域。

这对后续制作大量地图很重要。否则地图看起来能走，实际到处卡住，或者看起来不能走却能穿过去。

## 第五批：水域、地形高度和特殊地形

武侠地图会有很多水边、山路、桥、台阶、山门、雪地、沙漠。

需要先验证几类常见地形：

- 普通地面：正常行走。
- 石路/官道：正常行走，可用于路线表现。
- 草地/荒地：正常行走，可加脚步或速度差异，第一版可不做。
- 水域：默认不可走，浅水或桥上例外。
- 高台/台阶：能表现上下层关系。
- 桥梁：角色在桥上，水在桥下。
- 山壁/悬崖：不可走。
- 雪地/沙漠：可作为后续区域地形模板。

第一版不需要复杂物理，但需要把地形类型抽象出来，不能所有地面都只是“能走/不能走”。

## 第六批：植被、装饰物和氛围效果

一个能让人放心的地图 demo，不能只有地表和建筑。

建议加入：

- 草丛。
- 花木。
- 大树。
- 竹林或树林边界。
- 石头。
- 路牌。
- 旗帜。
- 灯笼。
- 水面动画。
- 飘动的云、雾、雪、落叶或尘土粒子。

这些可以先用临时素材，但要验证项目支持：

- 静态装饰物。
- 可遮挡装饰物。
- 可碰撞装饰物。
- 循环动画装饰物。
- 粒子氛围层。

漂浮云朵、薄雾、落叶这类东西不只是好看，它们能证明场景不只是“功能测试图”，而是能走向正式视觉表达。

## 第七批：相机、比例和角色尺度

当前地图让人没底，很大一部分可能来自比例感不对。

需要明确：

- 主角在屏幕中大概占多高。
- 一栋房屋相对主角有多大。
- 一条路能容纳几个人并排。
- 一个村镇场景大概有多少屏。
- 世界地图和局部场景是否使用同一种比例。

需要验证：

- `Camera2D` 跟随主角。
- 相机不会显示地图外空白。
- 可配置缩放比例。
- 大场景移动时不抖动。
- UI 不受相机缩放影响。

如果比例没有定，后面所有美术资源都会难以统一。

## 第八批：交互点和场景入口

地图表现层 demo 也需要接上游戏逻辑，但不需要复杂剧情。

至少支持：

- NPC 对话点。
- 建筑入口。
- 场景传送点。
- 可拾取物。
- 告示牌或调查点。
- 触发区域。

示例：

```text
走到客栈门口 -> 显示进入提示 -> 进入客栈内部场景
走到药铺掌柜旁 -> 按键对话 -> 打开商店或测试对白
走到河边包裹 -> 拾取物品 -> 包裹消失并存档
走到村口 -> 切换到山道
```

这批的重点是证明“表现层”和现有任务、对话、物品、场景切换系统能接上。

## 第九批：地图编辑和配置工作流

朋友提到编辑器功能，这点是对的。

如果后续要持续做很多地标和场景，不能每次都靠手写节点和脚本。

这里建议采用“外部项目编辑器 + 结构化配置 + Godot 运行时”的工作流。

外部编辑器适合负责：

- 地图底图
- 图块或大图模式
- 建筑
- 装饰物
- 遮挡层
- 碰撞区
- 水域
- 粒子
- 相机边界
- 场景内视觉比例
- NPC 放置
- 对话绑定
- 任务绑定
- 拾取物
- 传送目标
- 剧情条件
- 地图对象状态
- 书线和势力状态

Godot 适合负责：

- 读取编辑器产出的配置。
- 加载图片、动画、粒子等资源。
- 运行时创建节点和碰撞。
- 执行移动、交互、战斗、对话、存档。
- 提供游戏内调试显示。

AI 适合负责：

- 批量生成对象配置
- 检查 id 是否重复
- 检查对话、任务、物品、目标场景是否存在
- 根据剧情表补 NPC、传送点、拾取物、事件条件
- 把表格整理成 `maps.json` 或其他结构化数据

需要考虑：

- 外部编辑器配置文件格式。
- 编辑器和游戏运行时是否共用同一份配置。
- 编辑器是否支持导入底图并在上面摆放对象。
- 编辑器是否支持编辑碰撞区、遮挡区、交互区、传送区。
- 编辑器是否支持预览角色比例、建筑比例、相机范围。
- 编辑器是否支持导出 Godot 可直接读取的数据。
- 地图对象命名规范。
- 碰撞区、交互区、传送区怎么配置。
- NPC 怎么放置和绑定对话。
- 建筑入口怎么配置目标场景。
- 地图状态怎么影响对象显示。
- 调试时如何显示可走区、阻挡区、交互区。
- 是否需要一个简单的地图对象配置表。
- 是否需要运行时调试开关显示对象 id、碰撞区、交互半径、传送目标。
- 是否需要一个校验脚本检查地图数据和场景节点是否一致。

第一版外部编辑器不用很完整，但至少要形成一种稳定工作流：

```text
导入底图/图块 -> 放置对象 -> 配置 id -> 配置类型 -> 配置交互/碰撞/遮挡/状态 -> 导出配置 -> 游戏运行测试
```

否则后面每张地图都要问“这个对象怎么接事件”，制作速度会很快掉下来。

建议顺序是：

```text
第一步：明确地图配置文件格式
第二步：外部编辑器能导入底图并摆放对象
第三步：游戏能读取编辑器导出的配置并生成地图
第四步：补碰撞、遮挡、交互区、传送区可视化编辑
第五步：补调试显示和数据校验
第六步：再考虑更复杂的事件、时间、势力行为编辑
```

也就是说，后续剧情负责人不一定要每天手动摆地图。更理想的工作方式是：

```text
AI 帮忙生成/修改地图数据
-> 用外部编辑器查看和微调
-> 运行游戏验证真实表现
-> 发现问题后继续让 AI 调整数据或让底层补工具
```

## 第十批：性能和资源规模

如果支持大图或大量装饰物，需要提前验证性能边界。

建议 demo 做一个稍微大一点的场景，不要只做一屏。

需要观察：

- 大图导入后内存是否可接受。
- 相机移动是否流畅。
- 多 NPC 是否卡顿。
- 粒子效果是否影响明显。
- 大量装饰物是否需要分层或合批。
- 是否需要地图分块加载。

第一版不一定要做地图流式加载，但至少要知道：

- 单张大图最大建议尺寸是多少。
- 一个场景建议多大。
- 一张地图放多少 NPC 和装饰物比较稳。
- 什么时候需要拆场景。

## 建议的 Demo 场景

建议先做一个“山脚村镇升级版”或“江南小镇测试场”。

它比世界地图更适合验证表现层，因为里面能同时放建筑、人物、水、桥、树、遮挡、入口和 NPC。

场景内容可以包括：

- 一张村镇或小镇地图底图，或图块拼接地图。
- 主角四方向行走动画。
- 两到三个 NPC。
- 客栈、药铺、民居、告示牌。
- 一条河或池塘。
- 一座桥。
- 几棵可遮挡的大树。
- 一段不可走的墙或山壁。
- 一个山道出口。
- 一个官道出口。
- 少量云雾、落叶或水面动画。
- 一个可拾取物。
- 一个能进入的建筑或临时内景。

这个 demo 做出来后，基本就能判断项目地图底座是不是可靠。

## 可以直接发给同伴的版本

我重新想了一下，我现在最没底的不是大地图以后有没有动态事件、时间流逝、势力行为这些上层系统。那些后面当然重要，但不是当前最核心的问题。

我真正没底的是地图表现层和场景制作管线。现在看到的地图还是太像临时像素块测试场，我不知道以后怎么往里面稳定填城镇、山门、山道、建筑、NPC、水域、植被和剧情入口。

所以下一阶段我更希望先做一个“地图表现层 demo”，用来证明项目能做出接近正常 RPG 场景的地图，而不是继续停留在功能测试图。

这个 demo 可以先选“山脚村镇升级版”或“江南小镇测试场”，不用很大，但要尽量覆盖常见地图能力：

1. 支持导入正常图片资源。地图可以验证两种路线：一是大图底图模式，二是图块拼接模式。至少要明确后续地图到底主要靠哪种方式制作。

2. 角色不能只是像素点。主角要支持上下左右行走动画、待机动画；NPC 至少能用正常图片站立，最好也支持简单行走。角色资源要能替换，不能写死某一套素材。

3. 建筑和树木要支持遮挡。比如角色走到房屋屋檐、大树树冠、山门牌楼后面时，会被正确挡住；走到前面时又显示在前面。

4. 地图要有明确碰撞和路径阻断。房屋、墙、山壁、树干、水域、地图边界不能随便穿过去。最好有调试显示，可以看到碰撞区、可行走区、交互区、传送区。

5. 要支持水域、桥、台阶、高低层这类基础地形。第一版不用复杂物理，但至少要证明水不能走、桥能走、台阶或高台能表达层级。

6. 要支持植被和装饰物。草丛、树、石头、路牌、旗帜、灯笼这类对象，有的只是装饰，有的有碰撞，有的能遮挡。

7. 要支持氛围效果。比如水面动画、飘动云雾、落叶、雪、尘土粒子之类，先用临时素材也可以。关键是证明场景能从功能测试图走向有画面感的地图。

8. 要定角色和场景比例。主角多高，房屋多大，道路多宽，一个村镇大概几屏，这些要先有感觉，否则后续所有素材都不好统一。

9. 要接上基础交互。NPC 对话、客栈入口、药铺入口、告示牌、可拾取物、村口传送到山道，这些不需要复杂剧情，但要证明表现层能和现有对话、物品、场景切换系统接上。

10. 要解决“只能运行后才知道地图长什么样”的问题。现在很多地图内容是运行时由脚本和数据生成的，所以打开 Godot 编辑器只看到很空的场景。这不一定要改成 Godot 内编辑，但至少要有一个外部地图编辑器，能看到底图、建筑、遮挡、碰撞、水域、植被、粒子、交互区和相机边界。

11. 要考虑地图制作工作流。后面如果持续做很多场景，需要有稳定方式配置对象 id、碰撞区、遮挡区、交互区、传送目标、NPC 对话、对象状态。第一版编辑器不用很完整，但要能导入底图、摆对象、画区域、导出游戏可读配置。

另外，有些能力现在已经有雏形，比如角色帧图片加载、数据化地图对象、基础碰撞阻挡、战棋地形配置等。这些不需要重复从零做，但需要在新的地图表现层 demo 里验证它们是否能用于正式场景，而不是只服务于临时测试图。

简单说，我希望下一阶段先别急着做动态世界系统，而是先做一个让人放心的地图场景 demo。只要这个 demo 能证明“正常 RPG 场景可以做出来”，我这边才好继续往里面填地标、剧情、人物和事件。

更具体一点，这个 demo 里最好有：一个小镇或村镇场景、主角四方向动画、两三个 NPC、客栈和药铺、房屋遮挡、大树遮挡、一条河、一座桥、不可走的墙或山壁、一个可拾取物、一个传送出口、一些植被和云雾/落叶/水面动画。

这批做出来以后，再往上做时间流逝、事件系统、势力行为、大地图动态状态这些就更踏实。否则上层系统即使想清楚了，底下的地图画面和制作管线不稳，我这边还是没法放心推进内容。
